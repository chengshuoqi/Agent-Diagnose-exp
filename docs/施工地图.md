## 0. 摘要

**三条事实**

1. 管线跑得通，但 `output/scores.json` 与 `output/trajectories/` **不是同一次运行的产物**，8/10 条对不上。
2. 拼接键是**文件名**（`= task_id`）。`task_id` 稳定、内容不稳定，所以错配**不发生任何报错**。
3. 因此 `output/correlation.md` 里的 `r=0.63` 不对应任何真实量——不是有偏，是**无意义**。

**两个目标**

| 目标 | 手段 | 完成标志 |
|---|---|---|
| 让错配**不可能通过** | 来源指纹 + 拒算 + run 隔离 | 拿错配输入跑 `correlate` 会 exit 2 而不是出数 |
| 让「没数据」**说得清** | N/A 不进均值 + 报 `n_available` | `backtrack` 行显示「样本不足 (n=1)」而不是 `-` |

**不做**：架构重构。理由与完整清单见 §6。

一句话概括这张图的立场：**这次施工不改实验的科学设计，只改「数值与数据之间的对应关系」**。前者需要新的实验，后者只需要让错误显形。

## 1. 证据：为什么不能「直接重跑一遍」

完整对照表见 [`docs/evidence/baseline-drift.md`](evidence/baseline-drift.md)。摘录：

| task_id | 分数表 (steps, success) | 轨迹 (steps, success) | 判定 |
|---|---|---|---|
| `t01_backpack_first_price` | (2, True) | (1, False) | 漂移 |
| `t02_add_home_product` | (2, True) | (0, False) | 漂移 |
| `t03_cheapest_backpack` | (2, True) | (1, False) | 漂移 |
| `t04_coffee_under_20` | (8, False) | (0, False) | 漂移 |
| `t05_no_results` | (2, True) | (2, True) | 一致 |
| `t06_product_page_price` | (3, True) | (2, False) | 漂移 |
| `t07_cart_status` | (2, True) | (0, False) | 漂移 |
| `t08_most_expensive_backpack` | (2, True) | (2, True) | 一致 |
| `t09_vague_kitchen` | (4, None) | (2, None) | 漂移 |
| `t10_vague_gift` | (8, None) | (1, None) | 漂移 |

时间线：`scores.json` 写于 `2026-11-11T15:30:37`，轨迹写于 `2026-11-14T16:22:04 ~ 16:23:02`。

**「直接重跑一遍」为什么不够**：重跑只会换一批数据，**不会改变拼接键**。下一次仍然用文件名 join，仍然可能在两次运行产物混放时静默错配——只不过这次你未必发现。这就是必须动代码而不是动数据的理由。

**三个根因**

| 根因 | 位置 | 后果 |
|---|---|---|
| 拼接键是文件名 | `code/correlate.py:148-155` | 错配无报错 |
| 分数行无来源信息 | `code/score_trajectories.py:174-181` | 无法判断错配 |
| 输出无 run 隔离 | `code/run_episodes.py:192-196` | 批次互相覆盖 |

## 2. 质量属性场景（借 ATAM 的骨架，只借骨架）

ATAM 的做法是：先写**可度量的场景**，再看架构满不满足。这里只取它最有用的两样东西——**场景表**与**权衡点表**，不搬全套流程。

| ID | 场景（刺激 → 响应 → 度量） | 现状 | 由谁保证 |
|---|---|---|---|
| QAS-1 | 把两次运行的产物混在一起喂给 `correlate` → **拒算** → 报错且不产出文件 | ✗ 静默出数 | #2 |
| QAS-2 | 任取一条分数 → **能说出**它来自哪条轨迹、哪个模型、哪版 prompt → 5 个字段齐全 | ✗ 只有 `task_id` | #1、#4 |
| QAS-3 | 重跑一次采集 → 不覆盖上一次 → `output/runs/` 下并存两个目录 | ✗ 覆盖 | #3 |
| QAS-4 | 某维度 9/10 为 N/A → **输出上能看出**「样本不足」而非 `-` → 表中有 `n_available` 与非 N/A 计数 | ✗ 打印 `-` | #5 |
| QAS-5 | 删除同级 `AgentDiagnose-main` 克隆 → 评分仍可运行 → 不报 `FileNotFoundError` | ✗ 硬依赖外部路径 | #4 |

QAS-1 是**主场景**：其余四条都是为了让 QAS-1 的失败可解释。若只能保一条，保它。

## 3. 权衡点

软件工程的「思考」大部分落在这张表里：**选了什么、放弃什么、为什么这个代价可以接受**。

| # | 权衡 | 选的 | 放弃的 | 代价 | 为何接受 |
|---|---|---|---|---|---|
| T1 | 哈希口径 | canonical JSON 的 sha256 | 原始字节 sha256 | 多一个规范化函数 | 原始字节对缩进/换行/编码敏感，一次 re-serialize 就误报；要判断的是「内容变没变」 |
| T2 | 错配处置 | **拒算**（exit 2） | 自动修复 / 仅警告 | 需要人重跑 | 自动修复要猜「哪边才是对的」，猜错比报错更贵 |
| T3 | 输出布局 | `output/runs/<run_id>/` | 保持固定 `output/*.json` | 路径变长、文档要改 | 固定路径正是覆盖事故的成因；一行路径换来批次不可互相毁灭 |
| T4 | N/A 处理 | 改**聚合**（N/A 不进均值）+ 报 `n_available` | 改 rubric（重定义 1–4 分） / 插补 | 总分与论文不可直接比 | 改 rubric 就失去与论文的可比性；插补会伪造方差 |
| T5 | prompt 依赖 | 仓内快照 + 哈希 | git submodule / 继续读同级克隆 | 上游更新需手动同步 | submodule 增加克隆复杂度；而我们要的是「文本永不漂移」 |
| T6 | 施工范围 | 只修**数据对应关系** | 架构重构（拆模块/schema/测试） | 代码形状不变，仍然难测 | 见 §6——重构不产生可对比的数据，而这次施工的产出必须是数据 |

**T6 是主权衡**，其余五条都是它的下游。它的反面（「那就重写吧」）在 §6 逐条给出拒绝理由。

## 6. 不做清单（负向设计）

**在有限预算里，说清「不做什么」比多做一件更值钱**——因为每一项都对应一种看起来正确、实际会失败的诱惑。

| 不做 | 诱惑在哪 | 为什么不做 | 若要做的前置条件 |
|---|---|---|---|
| **不建 `schema.py`**（轨迹/分数行的唯一定义） | 形状被手写 5 遍，抽取它「明显更干净」 | 它**不改变数据，只改变代码形状**；不产生任何可对比的数据 | 先有 G1/G2 的证据，再谈形状；且需连上游 `from_json` 一起对齐，会越出本仓边界 |
| **不拆模块 / 不做依赖注入** | 现在 `run_task` 拿 `argparse.Namespace`，难测 | 同上；且一改就是大范围 diff，与「一次只让一件事变可信」冲突 | 有 pytest 覆盖之后再动 |
| **不加 pytest** | 没有测试显得不专业 | 没有 schema 就没有稳定的测试目标；先测字符串解析是低价值测试 | G1 完成后，先把 `correlate.self_test` 提升为真 runner（它已在仓库里，只是没人调用） |
| **不 fork / 不修上游** | 上游 dashboard 因 `.gitignore` 吃掉 `lib/` 而不可用，很想修 | 无 LICENSE，且投入产出与课程目标无关 | 若要长期维护再看 |
| **不动 `nnetnav-live/`（3.5GB）** | 论文的 46k→6k 筛选就在那 | 不属于本仓库；纳入会毁掉「clone 即可复现」 | 单独立项，且需算力预算 |
| **不改 rubric 的 1–4 分定义** | `backtrack` 分数难看，想改锚点 | 改了就不能与论文 Table 1 对话 | 明确要做「独立研究」而非「复现」时 |
| **不写工期与排期** | 汇报时很想给甘特图 | 时间估计在这里不承担决策功能，只会制造「按计划完成」的假象；本图的顺序是**依赖顺序** | — |

## 7. 与两个结果目录的关系

| 目录 | 内容 | 是否可用于结论 |
|---|---|---|
| `output/runs/A-baseline/` | 复现现状：同一次运行采集的 10 条轨迹 + 10 条 judge 分 | **否**。provenance 自洽，但标注若为 AI 模拟则仍是「AI 对 AI」；它是一份**干净的基线** |
| `output/runs/B-refactor/` | G1/G2 之后重跑的结果 | **是**（在有真实人工标注的前提下），因为每条分数都能追到唯一一条轨迹 |

**对比设计**：A 与 B 用**同一任务集、同一 judge、同一标注口径**，唯一变量是「来源是否被绑定」。这样 A→B 的差异可以归因到施工本身，而不是「又跑了一次」。

**A 的定位要说清**：它是基线，不是复现结果。论文 Table 1 用的是人类标注；在换成真实人工标注之前，A 里的相关系数只能标注为「管线跑通」。

## 8. 失败信号（什么时候应该停下）

判断「施工」和「环境」的分界线，比判断「成功」更重要：

| 信号 | 说明 | 该做什么 |
|---|---|---|
| `correlate` 对**全部** task 拒算 | 哈希口径不一致（很可能是 canonical 形式实现有两份） | 检查是否只有一处实现，而不是各处各写一遍 |
| A 目录里 >3 条轨迹 `error` | Dify / WebArena 环境问题，不是代码问题 | 先修环境，不要开始改代码 |
| `scores.json` 的 `n_steps` 与轨迹 `len(actions)` 系统性差 1 | 计数口径分歧（`meta.n_steps` 是否含最后一动作） | 先统一口径再谈哈希 |
| 加了 2 条难度任务后 `backtrack` 仍全是 N/A | 任务是「难」而不是「需要回退」 | 回看任务设计，不要加大任务量 |
