# 实验报告：AgentDiagnose 的复现、诊断与可信化改造

> 对象论文：*AgentDiagnose: An Open Toolkit for Diagnosing LLM Agent Trajectories*（EMNLP 2025 Demo）
> 上游仓库：<https://github.com/oootttyyy/AgentDiagnose>　实验仓库：<https://github.com/chengshuoqi/Agent-Diagnose-exp>
> 相关文档：[施工地图](施工地图.md) · [验收记录](验收记录.md) · [产物取证](evidence/baseline-drift.md) · [标注说明](标注说明.md)

---

## 0. 摘要

我们用 WebArena shopping + Dify 复现了论文的**实验一**（LLM judge 按五维 rubric 给轨迹打分，再与人工标注做相关性），
目标是复现 Table 1 的量级。复现过程中我们没有得到一组"能写进报告的数"，得到的是**三组互相矛盾的数**：

| 批次 | 五维 r 均值 | 成功率 | 被网络截断的轨迹 |
|---|---|---|---|
| A 基线（改造前） | **0.81** | 4/10 | 5/10 |
| 中间批（已判无效） | 0.90 | — | 5/10 |
| B 施工后（有效） | **0.47** | 7/10 | 0/10 |
| 论文 Table 1（n=30） | 0.57 | — | — |

同一套 rubric、同一个 judge、同一个标注人，两批数据的相关系数差了 0.34，而**成功率更高的一批 r 反而更低**
（7/10 对 4/10）。我们把原因定位到**两列分数的方差结构不对称**，而不是 rubric 或 judge 的差异。

因此本报告的主张不是"我们复现出了 0.57"，而是三件更小、但站得住的事：

1. **原文的 Table 1 在仓库层面不可验证**——它的分数与轨迹之间没有任何绑定，且仓库里根本没有那 30 条标注数据（§3）；
2. **这种管线会静默产生"看起来有效"的错误结果**——我们自己的第一批数据里就有 8/10 条分数与轨迹错配（§3.1）；
3. **在 n=10、单标注人、无标注者间一致性的条件下，相关系数不是稳定量**——它随标注尺度漂移，量级超过它与论文的差距（§5）。

对应的工程改造补上了"产物级 provenance"，并把"错配"从"看不出来"变成"算不出来"（§4、§6）。

---

## 1. 对象与问题

### 1.1 论文在做什么

给定一条 agent 轨迹 $T=\{(o_i,r_i,a_i)\}_{i=1..n}$（观测 / 推理 / 动作序列），用 LLM-as-judge 按 1–4 分
给五个维度打分，再与人类标注做相关性。五个维度是：回溯探索、任务分解、观测阅读、自我验证、目标质量。
论文报告五维平均 Pearson r=0.57（n=30），并把它当作"这个 rubric 能替代人工"的证据。

### 1.2 我们的三个问题

1. 论文的 CLI 链路能不能在本地跑通，跑出来是什么量级？
2. 如果对不上，差在哪——rubric、judge、还是数据？
3. 一个"复现实验"要满足什么条件，它的数字才值得写进报告？

问题 3 是这次工作的重点。前两个问题给了我们回答它的素材。

---

## 2. 复现：把链路跑通

链路四步（详见 README §3）：Dify agent 在本地 shopping 站点执行 10 条任务并记录轨迹 → Dify 扮演 judge
按 rubric 打分 → 生成标注表供人工打分 → 算相关性。

10 条任务覆盖五类：直接检索（t01/t03/t08）、需要进详情页（t06）、多条件筛选（t04）、负结果（t05）、
含糊目标（t09/t10）。含糊任务是为了给 `objective_quality` 制造方差。

第一轮跑出来的数是 **0.83 / 0.84 / 0.78 / 0.79（均值 0.81）**，比论文的 0.57 高出一大截。
这个"好消息"引出了问题 3：它可信吗？

---

## 3. 诊断：三个发现

### 3.1 发现一：分数与轨迹之间没有绑定（8/10 条错配）

把第一轮的产物按时间排一下就露馅了：

```
output/scores.json          2026-11-11 15:30
output/trajectories/*.json  2026-11-14 16:22   ← 晚三天
```

逐条比对 `n_steps` / `success`，**8/10 条对不上**（完整对照表见 [`evidence/baseline-drift.md`](evidence/baseline-drift.md)）：

| task_id | 分数表 | 磁盘轨迹 | |
|---|---|---|---|
| t01_backpack_first_price | (2 步, 成功) | (1 步, 失败) | 漂移 |
| t04_coffee_under_20 | (8 步, 失败) | (0 步, 失败) | 漂移 |
| t05_no_results | (2 步, 成功) | (2 步, 成功) | 一致 |
| … | | | 8/10 漂移 |

`correlate.py` 当时的拼接键是**文件名**（`task_id`）。文件名稳定、内容每次重跑都变，所以这种错配
**不会触发任何报错**——它只会安静地算出一个相关系数。

这不是我们的实现缺陷，而是照抄了上游的做法：上游 `evaluate_trajectories.py:42` 同样用
`json_file.stem` 当 id，而且 `:100-119` 还有一层更糟的逻辑——**只要结果文件里已有同名 id，就跳过重算、复用旧分数**。
所以"重跑一批同名轨迹"在上游会直接得到旧分数，且打印 `Loaded N existing results. 0 trajectories remain.`。

### 3.2 发现二：流式请求没有重试，网络抖动会毁掉整条轨迹

Dify 的 Agent 应用只接受 streaming 响应。而客户端里的 `retries` 参数只作用于 blocking 分支
（`dify_client.py:63-95`），流式分支（`_chat_stream`）一次 TLS 抖动就直接抛——**实际零重试**。

后果在数据里：A 批次 10 条轨迹里 5 条被
`URLError: [SSL: UNEXPECTED_EOF_WHILE_READING]` 截断，其中 2 条是 0 步的空轨迹。

补上指数退避重试后，同样一条曾崩溃的任务（t05）复跑得到 2 步、`success=True`、无 error。

### 3.3 发现三：headline 维度没有样本

论文里相关系数最低、也是讨论最多的维度是 `backtrack_and_explore`（0.39）。在我们的两批数据里：

- A：10 条标注中 9 条填 `N/A`，可用配对 **n=1**；
- B：10 条中 8 条 `N/A`，可用配对 **n=1**。

原因是任务设计——10 条 shopping 任务大多"一次走对"，没有回退机会。所以这个维度在我们这里
**不是精度差，是没有数据**。论文用 n=30 报出 0.39，我们连复现它的资格都没有。

---

## 4. 改造：只做两件事

面对上面三个发现，最容易的冲动是"重写整个管线"。我们没有这么做，理由是：**架构重构不产生任何可对比的数据**，
而这次工作的产出必须是数据。

### 4.1 两个目标

| 目标 | 手段 | 完成标志 |
|---|---|---|
| 让错配**不可能通过** | 轨迹指纹 + 拼接前校验 + 按批隔离 | 拿错配输入跑 `correlate` 会 exit 2，而不是出数 |
| 让「没数据」说得清 | N/A 不进均值并留痕、双列 n、备注 | `backtrack` 行显示「样本不足 (n=1)」而不是 `-` |

### 4.2 七项改动

| issue | 改动 | 关键点 |
|---|---|---|
| #1 | 分数行写入 `traj_sha256` / `run_id` / `judge_model` / `prompt_sha256` / `scored_at` | 哈希用 canonical JSON，只改缩进不算变 |
| #2 | `correlate` 拼接前重算哈希并逐条比对 | 同时校验**标注表生成时记下的 `n_steps`/`success`**，拦住"人标的是旧批次" |
| #3 | `output/runs/<run_id>/` 取代固定路径 | 已有文件默认跳过，`--overwrite` 才覆盖 |
| #4 | rubric prompt 快照进仓库 | 运行期不再读仓库外的克隆，`prompt_sha256` 才有意义 |
| #5 | N/A 不进均值 + `n（配对）`/`n（标注）` 双列 | 取消 pooled：41 个非独立观测的 n 是虚高的 |
| #6 | 标注表已填即拒绝写入；CSV 编码回退 | 这一步曾经真的清空过 50 格 |
| #7 | 排除 `*.failed.json`、去掉 `run_all` 的隐式 `--mock`、`reward` 三态 | 三条让产物"看起来有效"的污染路径 |
| #9 | 流式请求补重试；`correlate` 报告带 error 的轨迹 | 环境失败 ≠ 能力失败，必须能分开看 |

### 4.3 反向设计：不做什么

把"不做"写清楚，比多做一件更能说明判断力：

| 不做 | 理由 |
|---|---|
| 不建 `schema.py` | 它只改代码形状，不产生可对比的数据；且要对齐上游 `from_json`，越界 |
| 不拆模块 / 不做依赖注入 | 同上；先让每条数可信，再谈可维护性 |
| 不加 pytest | 没有 schema 就没有稳定的测试目标；`correlate.self_test` 已经能覆盖统计部分 |
| 不 fork 上游 | 无 LICENSE，且与本实验目标无关 |
| 不改 rubric 的 1–4 定义 | 改了就不能与论文对话 |
| 不写工期 | 时间估计在这里不承担决策功能 |

## 5. 结果：两次有效测量的对照

### 5.1 数字

| 维度 | A 基线 r (n) | B 施工后 r (n) | 论文 r (n=30) | 区间是否重叠 |
|---|---|---|---|---|
| backtrack_and_explore | – (1) | – (1) | 0.39 | 无法比较（n=1） |
| task_decomposition | 0.83 (10) | **0.16 (10)** | 0.78 | 否（B 的 CI 上界 0.72 < 0.78） |
| observation_reading | 0.84 (10) | 0.37 (10) | 0.62 | 是 |
| self_verification | 0.78 (10) | 0.57 (10) | 0.56 | 是 |
| objective_quality | 0.79 (10) | 0.79 (10) | 0.54 | 是 |
| **五维均值 / overall** | **0.81** | **0.47** | **0.57** | 是 |

n=10 时 Pearson 的 95% 区间极宽（例如 B 的 `task_decomposition` 是 `[-0.53, +0.72]`）。
**除了 task_decomposition 勉强越界，其余每一维的区间都覆盖论文值**——我们既不能证实也不能证伪 0.57。

### 5.2 为什么两批差 0.34：不是 rubric，是方差结构

把两批的分数分布摆在一起，机制就清楚了：

| 维度 | A 人工分 | A 均值 | B 人工分 | B 均值 |
|---|---|---|---|---|
| task_decomposition | 4,4,1,3,1,2,4,4,4,3 | 3.00 | 4,4,4,2,4,4,4,4,4,3 | **3.70** |
| observation_reading | 4,4,1,2,1,2,4,3,4,3 | 2.80 | 4,4,3,2,4,4,4,3,4,3 | **3.50** |
| self_verification | 3,4,1,1,1,1,4,3,4,2 | 2.40 | 3,4,3,2,4,4,4,3,4,2 | **3.30** |

- **A 的人工分覆盖 1–4 全区间**，而 B 向 4 聚集（三个维度都没有 1 分）；
- 两批的**机器分分布相近**（都有 1–4）；
- 结果：A 的两列方差相当，r 高；B 的人工列方差塌缩，r 被少数几个低分样本支配。

我们另外检查了"截断是否解释 A 的高相关"：**在 A 内部剔除 5 条截断轨迹后，r 并未下降（n=5 时均值 0.86）**。
所以截断不是 A 高相关的原因，截断是另一件独立的问题（它污染数据，但不抬高 r）。

更可能的解释是**标注尺度漂移**：两批标注相隔三小时，同一个人，但 B 的 agent 明显更好
（成功率 7/10 对 4/10），标注人于是把"没出错"整体读成"4 分"。**单人标注无法把"尺度漂移"与"真实差异"分开。**

### 5.3 一个反直觉的结论

**agent 变好了（成功率 4/10 → 7/10），相关系数却掉了（0.81 → 0.47）。**

这不是悖论，它说明相关系数测的是"人和机器是否用**相同的相对顺序**打分"，不是"agent 好不好"。
当所有轨迹都被打得差不多好时，排序信息消失，r 自然塌掉。

所以把 r 当成质量指标是错的；把它当成**两个评分器的一致性指标**才对——而一致性会随样本分布剧烈变化。
这正是论文只用 n=30、单标注人、不报标注者间一致性时最大的漏洞：**0.57 这个数没有误差棒，而误差棒比它本身还大。**

---

## 6. 我们证明了什么，没证明什么

**证明了**

1. 原文仓库缺产物级 provenance，其核心指标在仓库层面不可复核（`evaluate_trajectories.py:42, 100-119`）；
2. 这类缺失会造成**静默错误**：我们自己的第一轮 8/10 条错配，没有任何报错；
3. 把 provenance 从"日志"升级为"拒算门槛"是可执行、可验收的（§4.2、[验收记录](验收记录.md)）；
4. 在 n=10 的规模下，相关系数对标注尺度极度敏感，量级差异（0.34）超过它与论文的差距（0.24）。

**没证明**

1. 论文的 0.57 是错的——我们的两个点都在它的区间内；
2. 我们的 rubric 实现有偏差——用的是与上游逐字一致的 prompt 快照（`--check-prompts` 可复验）；
3. 我们的改造让结果"更好"——改造只让结果**可验证**，数值上下波动是采样与标注的事。

---

## 7. 局限

| 局限 | 影响 | 若要修 |
|---|---|---|
| 单标注人，无 Cohen's κ | 无法区分尺度漂移与真实差异 | 两人独立标注 10 条并算 κ |
| n=10 | 区间宽到覆盖论文值 | 扩到 30–50 条（与论文同量级） |
| 任务偏简单 | `backtrack` 两批都是 n=1，headline 维度无数据 | issue #8：补 2 条必须回退的任务 |
| judge 单次调用 | 未测 judge 抖动（README 自述可能差 0.2） | 每条判 3 次取均值 |
| A 批次 5/10 截断 | A 只能当"旧口径污染批次"，不能当干净基线 | 用新客户端重跑 A |
| Dify 背后的模型不可见 | `judge_model` 只能记 `dify:unknown@host` | 换直连 API 并写明模型名 |

---

## 8. 结论

这不是一次成功的"复现"，而是一次成功的"证伪实验"——**我们证伪了"这个管线的单个相关系数可以当结论"这件事本身**。

如果要给这个工作一句定位：

> 我们没有让 AgentDiagnose 更准，我们让它**没法安静地给出一个错的数**：分数必须绑定到唯一一条轨迹，
> 缺失必须显示为缺失，环境失败必须与能力失败分开。做完这些之后，我们终于拿到了一个可以讨论的 0.47——
> 它比之前的 0.81 低得多，但它是第一个我们敢写进报告的数。
